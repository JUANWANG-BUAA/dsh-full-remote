# 0.5.0 传输优化 Benchmark

## 结论先行

与**已有 gzip 的旧版**比较，这轮优化的主要收益是：

1. **热静态请求免回源、免重复编码**：4 个真实入口资源重复 10 轮，回源 40 → 0 次；本机累计 HTTP 下载耗时中位数 424.68 → 28.15 ms（−93.4%）。这不是手机页面加载速度提升 93.4%。
2. **后台停止无用轮询**：真实 React 新旧组件在模拟时钟下，隐藏 60 秒 RPC 50 → 0 次；正常可见仍为 50 次，不用降刷新频率冒充优化。
3. **首次资源字节几乎不变**：415,637 → 415,534 B，仅减少 **103 B / 0.025%**。旧版 gzip 的既有收益不能重复算成本次收益。
4. **不是每个场景都更快/更小**：304 完整下行 HTTP 字节 **+54.1%**；合成 JSON API 本机耗时 **+16.2%**；gzip-only 冷路径约 **+5.0%**；真实 vendor JS 和 index CSS 的 Brotli Q4 都比 gzip L6 稍大。

没有给“整个产品快 X%”这种无法由这些场景支持的统一结论。

## 1. 基线、环境和原始结果

- 基线：Git 0d4b48c8837ac4b11f3c477b1c04bde46c75f5d6；用 git archive 提取未经改写的旧源码，**不是将新版的压缩/缓存开关关闭来伪造旧版**。
- 当前版：随 **0.5.0 正式版**发布的传输优化实现；结果来自发布前保留的测量记录，没有为 benchmark 修改产品逻辑，也未因文档版本更新重新测量。精确的受测源码与资源 SHA-256 见原始 transport 记录；不以版本号代替受测字节身份。
- 环境：Apple M5 Pro / arm64 / macOS 内核 Darwin 27.0.0 / Node v26.12.0。
- HTTP：同一台机器的 loopback HTTP/1.1，串行请求，每次新建下游 TCP。没有 TLS、Cloudflare、移动网络、浏览器缓存或页面渲染。
- 15 个计入统计的配对轮次，另外 2 轮预热不计；3 个变体的顺序轮换并反转。所有字节有解码一致性断言，冷热回源数、编码选择也有断言。
- HTTP 资源来自本机真实 Harness frontend dist 的 index.html、2 个入口 JS、2 个 CSS：共 **1,480,308 B**。并非高重复填充文本，也不包含所有字体/懒加载资源。
- 另加 7,314 B **合成 JSON** 作为不缓存的负对照，不冒充实际聊天/会话 API 样本。
- 归档原始记录：[transport.json](./benchmarks/v0.5.0/transport.json)（逐轮数据、源码/资源 SHA-256、编码实测）、[polling.json](./benchmarks/v0.5.0/polling.json)（逐请求起止事件）、[session.json](./benchmarks/v0.5.0/session.json)（5 轮行为观测）。
- 易读汇总：[summary.json](./benchmarks/v0.5.0/summary.json)。这些是 0.5.0 的固定测量归档，不是动态读取本机结果。复现脚本仍生成 output/benchmarks/{transport,polling,session,summary}.json；output 是忽略目录，复现结果不会自动替换发布归档。

## 2. HTTP 对比结果

表内是**每个配对轮次**，而不是 15 轮累加；时间是各 HTTP 请求从发出到完整读完的时间之和，再取 15 轮中位数。不含后续客户端解压/一致性校验，不含页面渲染，不能叫 LCP。

| 场景 | 请求数/轮 | 旧版主体 B | 当前主体 B | 旧版回源 | 当前回源 | 旧版累计 HTTP ms | 当前累计 HTTP ms | 时间变化 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 冷设备，HTML + 4 个入口资源 | 5 | 415,637 | 415,534 | 5 | 5 | 42.08 | 25.61 | −39.1% |
| 同设备热读，4 资源 × 10 轮 | 40 | 4,148,120 | 4,147,090 | 40 | 0 | 424.68 | 28.15 | −93.4% |
| 同设备条件请求，4 资源 × 10 轮 | 40 | 0 | 0 | 40 | 0 | 24.10 | 17.51 | −27.3% |
| 合成 JSON 动态 API × 10 次 | 10 | 6,960 | 4,050 | 10 | 10 | 8.82 | 10.25 | **+16.2%** |

### 必须如何理解这些数字

- **冷**仅指新设备没有服务端静态 variant，不是新进程/空连接池。服务端与连接池已预热。
- 热读刻意不用浏览器缓存，以测代理缓存：旧版反复从上游读取并压缩；当前版从设备隔离 LRU 直接发已编码字节。热场景上游原始主体 **14,794,830 → 0 B/轮**；但下游仍收到约 4.15 MB，不能说客户端流量减少 100%。
- 浏览器若直接命中新鲜 immutable 缓存，旧版和当前版都可能不发网络请求，本实验不把这种已有能力算成本轮收益。
- 条件请求的 backend 在两版中都正确处理弱 ETag。因此**旧版本来就 304 / 主体 0 B**，当前新增的是免回源，不是将非零 body 变成 0。
- 当前缓存的 304 带 Cache-Control / Vary / Age 等更多元数据。40 次下行完整 HTTP 字节 **6,360 → 9,800 B（+54.1%）**，每次多 86 B；不能隐瞒这项开销。
- JSON 动态 API 的请求数和上游主体完全相同，证实没有错误缓存 API。该合成响应 Brotli 体积更小，但本机微小请求耗时反而更长，不代表所有 API 都会更快。

### 同编码对照：缓存收益不是靠换成 Brotli 得到的

| 场景 | 旧版 gzip ms | 当前 gzip-only ms | 当前协商 Brotli ms |
|---|---:|---:|---:|
| 冷设备入口资源 | 42.08 | 44.20 | 25.61 |
| 40 次热静态请求 | 424.68 | 27.88 | 28.15 |
| 40 次条件请求 | 24.10 | 17.63 | 17.51 |

当前 gzip-only 冷路径还有约 **5.0% 本机开销**；热路径即使不换编码仍大幅改善。Brotli 的客户端解压也可能较慢：含解压和断言的整段热循环 wall 中位数为旧版 447.31 ms、当前 gzip 48.53 ms、当前 Brotli 60.02 ms。不要用纯 HTTP 下载时间替代用户端完整成本。

### 波动范围

| 场景 | 旧版中位 / 样本 p95 ms | 当前中位 / 样本 p95 ms |
|---|---:|---:|
| 冷设备 | 42.08 / 45.60 | 25.61 / 27.29 |
| 热静态 | 424.68 / 446.87 | 28.15 / 33.04 |
| 条件请求 | 24.10 / 29.45 | 17.51 / 21.29 |
| 合成动态 JSON | 8.82 / 11.10 | 10.25 / 12.53 |

这里只有 15 轮，nearest-rank p95 恰是样本最大值，不是生产长尾 SLO 或置信区间。机器负载、Node/zlib 版本、网络、并发和资源变更均会影响时间，复测应以新结果为准。

## 3. 压缩体积与编码成本

另做每文件、每算法 3 次预热 + 20 次同步编码，交替算法顺序。这是算法编码耗时，不是生产异步 worker 的吞吐或总 CPU 利用率。

| 资源 | 原始 B | gzip L6 B | Brotli Q4 B | gzip 编码中位 ms | Brotli 编码中位 ms |
|---|---:|---:|---:|---:|---:|
| index JS | 633,282 | 213,609 | 212,891 | 16.24 | 6.95 |
| vendor JS | 740,575 | 178,527 | 178,714 | 13.12 | 5.96 |
| vendor CSS | 29,288 | 8,066 | 7,680 | 0.20 | 0.13 |
| index CSS | 76,338 | 14,610 | 15,424 | 0.87 | 0.50 |

可见本批真实资源的收益更多在 **Q4 比 L6 编码耗时短**，不是首屏字节突然再省几十个百分点。质量等级不同，不是宣称 Brotli 算法在相同质量下全面优于 gzip。

## 4. 后台轮询 Benchmark

直接挂载 git archive 的**真实旧 RemoteSection**和当前真实组件，只 mock ProxyApi 的 status/sessions；使用 jsdom / React 18.3.1 / Vitest 4.1.10 模拟时钟，每 100 ms 推进并 flush React。不是按轮询间隔公式推算请求数。

所有窗口半开，启动请求算在第一个窗口：[0,60s)、[60,120s)、[120,180s)。隧道处于 online；快速 RPC 立即完成，慢 RPC 固定 5 秒，包括首次请求。

| 场景 | 旧版 RPC | 当前 RPC | 变化 |
|---|---:|---:|---:|
| 正常可见 60 秒 | 50（status 30 + sessions 20） | 50 | 0% |
| 从可见切隐藏 60 秒 | 50 | 0 | **−100%** |
| 隐藏后恢复可见 60 秒 | 50 | 50 | 0%，当前恢复瞬间刷新两类数据 |
| 5 秒慢 RPC，可见 60 秒 | 48 | 20 | **−58.3%** |
| 慢 RPC 峰值总在途数 | 5 | 2 | **−60%** |

慢场景单方法峰值：status 3 → 1，sessions 2 → 1，说明防止同类慢请求重叠，而不是全局只允许一个 RPC。慢请求减少不是刷新更快；隐藏期间没有补发积累轮询。

模拟器故意不施加真实浏览器后台 timer 节流，隔离应用层 visibility 行为。真实手机浏览器原本也可能节流/冻结旧版，因此 **50 → 0 不能直接外推成真实电池节省 100%**。已在途请求也没有因此被取消。只计算这两个本插件管理 RPC，不包括聊天或其他插件请求。

此 benchmark 多次复跑计数及 JSON 一致；普通可见请求频率没有下降。快速 Promise 的微任务排队造成的总并发瞬时差别不作性能宣传。

## 5. 活跃会话行为对比

用真实 HTTP/SSE 字节管道，store 时钟可控；活动场景 idle=1 秒，绝对 TTL 场景关闭 idle 以隔离变量。每 800 ms 发一事件，事件收完后 serialize 模拟持久化 sweep。每场景 5 轮，结果一致。它是确定性会话行为 benchmark，不是连续运行 80 秒的真实墙钟耐久/断网重连测试。

| 场景 | 旧版 | 当前 |
|---|---|---|
| 持续活动到模拟 80 秒，绝对 TTL=600 秒 | 1.6 秒已被 sweep 删除；原流仍开；新请求 303 | 101 个事件全部收到；session 保留；新请求 200 |
| 绝对 TTL=2 秒，仍每 800 ms 有字节 | 会话已失效但原流继续传递，模拟 4 秒仍收到数据 | 模拟 2.4 秒下一条事件到达时关闭；过期事件不交付，新请求 303 |

改善的是 idle 活动识别和失效连接清理，**不延长绝对 TTL，不保证断线事件无损恢复，不自动重放写操作**。idle 默认关闭，第一行收益针对启用了 idle timeout 的部署。

## 6. 复现

在仓库根目录，使用已经安装的依赖与上述 Git 基线；HTTP 测试需要真实 frontend dist。默认读取本机全局 Harness 的 dist，也可显式指定：

~~~bash
# 15 个测量轮次，2 个排除的预热轮次；每次热读/条件请求 10 轮
DSH_WEB_FRONTEND_DIST=/path/to/dsh-web-frontend/dist \
  BENCH_ROUNDS=15 BENCH_REPEATS=10 \
  node --experimental-strip-types scripts/benchmark-transport.mjs

# 真实 SSE，确定性 store 时钟，5 个配对轮次
node --experimental-strip-types scripts/benchmark-session.mjs

# 真实 React 新旧组件，模拟时钟与 RPC
NODE_ENV=test NODE_OPTIONS=--no-experimental-webstorage \
  pnpm exec vitest run --config scripts/bench-polling/vitest.config.ts

# 从以上三个原始 JSON 生成可携带汇总（含原始文件 SHA-256）
node scripts/summarize-benchmark.mjs

# 独立脚本静态检查
pnpm exec eslint scripts/benchmark-transport.mjs scripts/benchmark-session.mjs scripts/summarize-benchmark.mjs scripts/bench-polling
~~~

没有 checkout/reset 用户工作区，没有访问用户正在运行的会话；所有代理都仅绑定随机 loopback 端口，测试结束关闭。不同 benchmark 分开执行，避免相互争用 CPU。脚本读取本机 dist，**不执行其中的页面 JavaScript**。

## 7. 仍未测量

- 真实手机浏览器的页面 LCP/INP、滚动、耗电、弱网和实际隧道 RTT。
- 生产并发吞吐、持久化写入 IOPS、全进程 CPU / RSS / 堆峰值、长时间缓存驱逐压力。
- 聊天流增量编码、断线期间事件补齐、跨设备缓存共享（当前刻意禁止）。

因此不能从本文推导“整体快 93%”或“所有流量少 100%”。可以支持的结论是：**命中的热静态请求明显减轻代理/上游工作，隐藏与慢请求场景减少无用调用；冷加载体积几乎持平，部分元数据与动态请求有开销。**
